## 1. 为什么需要数据库？

回顾第 1 讲中的 `FAKE_DB: dict[int, dict]`。它存在以下问题：

| 问题 | 后果 |
|---|---|
| 数据保存在内存中 | 容器重启后全部丢失 |
| 仅存在于单个进程中 | 两个 API 实例拥有不同的数据 |
| 没有约束 | 无法阻止两个用户使用相同的邮箱 |
| 没有原子性 | 操作执行到一半发生崩溃，会留下不一致的状态 |
| 线性搜索 | 按标题查找物品需要遍历整个字典 |
| 没有并发控制 | 两个同时到达的请求可能预订同一个时间段 |

**数据库管理系统**（DBMS，法语缩写为 SGBD）能够统一解决这些问题。关系型数据库管理系统尤其提供了四项能力：

1. **持久化**：进程结束后，数据仍然存在。
2. **完整性**：即使应用代码存在错误，数据库也会拒绝不一致的数据。
3. **并发控制**：多个客户端可以同时写入，而不会破坏数据。
4. **声明式查询**：你描述想要获取**什么**，数据库引擎决定**如何**获取。

第 2 点最容易被低估。在 `users.email` 上设置 `UNIQUE` 约束，可以从数据库层面保证唯一性：应用程序错误、并发请求或写得不好的导入脚本，都不能插入违反该约束的重复值。

而 Python 中的检查，例如 `if User.query.filter_by(email=...)`，无法提供同样的保证，因为两个并发请求可能在任何一个执行插入之前，就同时通过检查。

> 对于项目：**把必须始终成立的规则放进数据库，而不只是写在 Python 代码中。**
>
> Python 代码用于生成友好的错误提示；数据库负责保证不允许错误数据进入。

顺便介绍一下你可能遇到的 NoSQL：MongoDB、Redis、Elasticsearch 面向其他需求，例如变化频繁的数据结构、缓存和全文搜索。它们通常不会以与关系型数据库相同的方式和严格程度，提供引用完整性与跨文档事务。

对于你们这样的结构化业务应用——用户、设备、预订之间具有紧密关系——**关系型数据库是合适的默认选择**，也是课程规定的选择。

## 2. 关系模型

关系模型由 IBM 的 **Edgar F. Codd** 于 1970 年正式提出，其核心思想很简单：使用关系，也就是表，表示数据，并通过定义明确的代数运算操作数据。

SQL 正是在这一基础上发展起来的，而关系模型在此后五十年间一直是行业的重要基础。

### 2.1. 表、行、列

一张**表**代表一种实体类型。每一**行**，也称为**元组**，代表一个实例；每一**列**，也称为**属性**，代表一个具有指定类型的特征。

例如，`items` 表：

| id | titre（标题） | tarif_jour（日租金） | owner_id（所有者 ID） |
|---|---|---:|---:|
| 1 | Vélo（自行车） | 8.50 | 3 |
| 2 | Perceuse（电钻） | 5.00 | 1 |

表头中的各项是列，下面的每条记录是一行。

### 2.2. 主键

**主键**用于唯一且稳定地标识一行记录。它不能为空，并且必须唯一。

建议使用自动递增的技术标识符 `id`，而不是业务数据。用户邮箱看起来具有唯一性，但如果某天用户想修改邮箱，所有引用它的记录都需要更新。

```sql
CREATE TABLE users (
    id    BIGSERIAL PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

`BIGSERIAL` 表示自动递增的 64 位整数。在较新的 PostgreSQL 中，对应的现代写法是：

```sql
BIGINT GENERATED ALWAYS AS IDENTITY
```

两种形式都可以使用。原文指出，`BIGSERIAL` 仍然非常常见，也是许多 ORM 使用的形式。

### 2.3. 外键与引用完整性

**外键**用于建立指向另一张表的关联，数据库管理系统保证该关联指向的记录确实存在。

```sql
CREATE TABLE items (
    id         BIGSERIAL PRIMARY KEY,
    titre      VARCHAR(120) NOT NULL,
    tarif_jour NUMERIC(8, 2) NOT NULL CHECK (tarif_jour > 0),
    owner_id   BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE
);
```

这样一来：

- 如果用户 999 不存在，就不能插入 `owner_id = 999` 的物品；
- `ON DELETE CASCADE` 表示：删除用户时，自动删除其拥有的物品。

`ON DELETE` 的行为属于**业务决策**，必须明确选择：

| 子句 | 删除父记录时的行为 |
|---|---|
| `ON DELETE RESTRICT` | 只要还存在子记录，就拒绝删除 |
| `ON DELETE CASCADE` | 同时删除子记录 |
| `ON DELETE SET NULL` | 将外键设为 `NULL`，前提是该列允许为空 |

对于 GearShare 项目：删除用户时，是否也要删除其过去的预订？还是应该保留预订历史？

这没有统一的正确答案，但你必须**作出决定并记录下来**。如果你没有明确说明，AI 智能体可能会悄悄替你作出这个决定。

*译注：原文将 `RESTRICT` 标为默认行为；严格来说，PostgreSQL 的默认行为是 `NO ACTION`，与 `RESTRICT` 在约束检查时机上存在区别。*

### 2.4. 关系基数

| 关系 | 建模方式 |
|---|---|
| **1–N，一对多**：一个用户拥有多个物品 | 在 `items` 表中放置外键 `owner_id` |
| **N–N，多对多**：一个物品有多个标签，一个标签也可对应多个物品 | 创建关联表 `item_tags(item_id, tag_id)` |
| **1–1，一对一**：一个用户对应一份个人资料 | 在其中一张表中设置带 `UNIQUE` 约束的外键 |

关联表示例：

```sql
CREATE TABLE item_tags (
    item_id BIGINT NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    tag_id  BIGINT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (item_id, tag_id)
);
```

**复合主键** `(item_id, tag_id)` 保证同一个标签不会重复关联到同一个物品。

### 2.5. 简单介绍规范化

规范化通过消除冗余来避免数据不一致。这里不展开完整理论，只需记住两个习惯：

- **不要重复存储同一条信息。** 如果所有者姓名同时存在于 `users.nom` 和 `items.owner_nom` 中，它们迟早会出现差异。应该保存 `owner_id`，再通过连接查询获取姓名。
- **一个列值应当具有原子性。** 在 `tags VARCHAR(255)` 中存放 `"velo,sport,ete"` 会让数据难以管理：无法方便地建立有效索引、准确搜索或保证一致性。应当建立独立的表。

有意进行反规范化，也就是通过重复数据提高速度，是存在的。但它应该是在**测量并确认性能问题之后**采取的优化，而不是默认做法。

## 3. 常用 PostgreSQL 数据类型

| 类型 | 用途 | 说明 |
|---|---|---|
| `BIGSERIAL` / `BIGINT` | 标识符 | `BIGSERIAL` 可用于主键 |
| `VARCHAR(n)` / `TEXT` | 字符串 | `TEXT` 不指定长度限制；`VARCHAR(n)` 明确长度约束 |
| `NUMERIC(p, s)` | **金额** | 精确数值，涉及金钱时使用 |
| `REAL` / `DOUBLE PRECISION` | 科学测量值 | **不要用于金额**，存在二进制浮点舍入问题 |
| `BOOLEAN` | 真／假 | `TRUE` / `FALSE` |
| `DATE` | 不含时间的日期 | |
| `TIMESTAMPTZ` | 带时区语义的日期时间 | 应优先于 `TIMESTAMP` 使用 |
| `JSONB` | 半结构化数据 | 可以建立索引；用于结构确实会变化的数据 |
| `UUID` | 全局标识符 | 当 ID 需要难以预测时有用 |

两个经典陷阱：

1. **用 `FLOAT` 保存欧元金额。** 二进制浮点运算中可能出现 `0.1 + 0.2 != 0.3`。日租金、账单总额、账户余额都应使用 `NUMERIC`。
2. **使用不带时区的 `TIMESTAMP`。** 用户、服务器和数据库可能处于不同时区，还要考虑夏令时。`TIMESTAMPTZ` 按 UTC 保存时间点，并进行时区转换，因此应优先选择它。

## 4. SQL：定义数据库结构（DDL）

**DDL**，即 *Data Definition Language*，数据定义语言，用于描述数据库结构。

```sql
CREATE TABLE users (
    id            BIGSERIAL PRIMARY KEY,
    email         VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    display_name  VARCHAR(80)  NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE items (
    id          BIGSERIAL PRIMARY KEY,
    owner_id    BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    titre       VARCHAR(120) NOT NULL,
    description TEXT,
    tarif_jour  NUMERIC(8, 2) NOT NULL CHECK (tarif_jour > 0),
    disponible  BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE reservations (
    id          BIGSERIAL PRIMARY KEY,
    item_id     BIGINT NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    borrower_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    date_debut  DATE   NOT NULL,
    date_fin    DATE   NOT NULL,
    statut      VARCHAR(20) NOT NULL DEFAULT 'active',
    CONSTRAINT dates_coherentes CHECK (date_fin > date_debut),
    CONSTRAINT statut_valide    CHECK (statut IN ('active', 'annulee', 'terminee'))
);
```

观察这一结构**禁止了哪些情况**：

- 没有所有者的物品：`NOT NULL` + `REFERENCES`；
- 负数或零租金：`CHECK`；
- 两个账户使用相同邮箱：`UNIQUE`；
- 预订结束日期早于开始日期：涉及两个列的 `CHECK`；
- 随意填写不合法的状态：`CHECK ... IN`。

这些约束可以在数据库层面防止对应的数据错误，不依赖应用代码是否正确。

**给约束命名**，例如 `CONSTRAINT dates_coherentes ...`。当约束被违反时，错误信息会更容易处理，你也可以将其转换成清晰的 HTTP `409` 响应。

修改已有表：

```sql
ALTER TABLE items ADD COLUMN categorie VARCHAR(50);
ALTER TABLE items ALTER COLUMN description SET NOT NULL;
ALTER TABLE items DROP COLUMN categorie;
```

⚠️ 在生产环境中，不应手动执行 `ALTER TABLE`，而应使用**纳入版本管理的数据库迁移**。第 4 讲将介绍 Alembic。

## 5. SQL：操作数据（DML）

```sql
-- 插入，并获取生成的 ID
INSERT INTO users (email, password_hash, display_name)
VALUES ('alice@esiee.fr', '$pbkdf2-sha256$...', 'Alice')
RETURNING id;

-- 批量插入
INSERT INTO items (owner_id, titre, tarif_jour) VALUES
    (1, 'Vélo de ville', 8.50),
    (1, 'Perceuse', 5.00),
    (2, 'Tente 2 places', 12.00);

-- 更新
UPDATE items SET disponible = FALSE WHERE id = 2;

-- 删除
DELETE FROM items WHERE id = 3;
```

`RETURNING` 是 PostgreSQL 中非常实用的功能：无需再向数据库发起第二次请求，就能取得生成的标识符。

> ⚠️ **不带 `WHERE` 的 `UPDATE` 和 `DELETE` 会作用于整张表。**
>
> 这是生产环境中破坏数据的常见原因。养成先写 `WHERE` 再补充其余部分的习惯，或者先用 `SELECT` 验证匹配范围。

### 6.1. SELECT、WHERE、ORDER BY

```sql
SELECT id, titre, tarif_jour
FROM items
WHERE disponible = TRUE
  AND tarif_jour <= 10
  AND titre ILIKE '%vélo%'
ORDER BY tarif_jour ASC
LIMIT 20 OFFSET 0;
```

结果：

| id | titre | tarif_jour |
|---|---|---:|
| 5 | Vélo enfant | 4.00 |
| 1 | Vélo de ville | 8.50 |

共 2 行。

逐项理解：

- 电钻 `Perceuse` 虽然只需 5 欧元，但因为不可用而被排除；
- 电动自行车 `Vélo électrique` 因为价格过高，15 欧元，而被排除；
- 帐篷 `Tente` 因为标题不含 `vélo` 而被排除；
- 按价格升序排序，因此儿童自行车排在前面。

`ILIKE` 是不区分大小写的 `LIKE`，属于 PostgreSQL 特有语法。`%` 可以匹配任意长度的字符序列。

它不区分大小写，但**仍然区分重音符号**：

```sql
titre ILIKE '%velo%'
```

在这个数据集中会返回 0 行，因为 `é` 不等于 `e`。要实现能够忽略重音符号的搜索，需要使用 `unaccent` 扩展——这是 AI 智能体很容易遗漏的细节。

`LIMIT` / `OFFSET` 用于实现分页，正好对应第 1 讲 FastAPI 路由中的 `limit` / `skip`。

### 6.2. 连接查询

连接是关系型数据库的核心：把分散在多张表中的信息重新组合起来。

```sql
SELECT
    i.id,
    i.titre,
    i.tarif_jour,
    u.display_name AS proprietaire
FROM items AS i
JOIN users AS u ON u.id = i.owner_id
WHERE i.disponible = TRUE;
```

结果：

| id | titre | tarif_jour | proprietaire |
|---|---|---:|---|
| 1 | Vélo de ville | 8.50 | Alice |
| 3 | Tente 2 places | 12.00 | Bob |
| 4 | Vélo électrique | 15.00 | Chloé |
| 5 | Vélo enfant | 4.00 | Bob |
| 6 | Ponceuse | 7.00 | Alice |

共 5 行。

`items` 表只保存了 `owner_id = 1`，连接查询负责从 `users` 表中找到对应的 `Alice`。

另外，如果没有 `ORDER BY`，结果的行顺序**没有保证**。这里看起来按照插入顺序排列，但不能依赖这一点。

| 类型 | 效果 |
|---|---|
| `INNER JOIN`，或简写为 `JOIN` | 只保留两侧能够匹配的记录 |
| `LEFT JOIN` | 保留左表全部记录；右侧没有匹配时填入 `NULL` |
| `RIGHT JOIN` | 与 `LEFT JOIN` 相反；较少使用，通常改写为 `LEFT JOIN` |
| `FULL OUTER JOIN` | 保留两侧全部记录 |

当关联记录可能不存在时，就需要 `LEFT JOIN`：

```sql
-- 列出所有物品及其预订数量，包括预订数量为 0 的物品
SELECT i.titre, COUNT(r.id) AS nb_reservations
FROM items AS i
LEFT JOIN reservations AS r ON r.item_id = i.id
GROUP BY i.id, i.titre
ORDER BY nb_reservations DESC;
```

结果：

| titre | nb_reservations |
|---|---:|
| Vélo de ville | 2 |
| Tente 2 places | 1 |
| Vélo électrique | 1 |
| Vélo enfant | 0 |
| Ponceuse | 0 |
| Perceuse | 0 |

共 6 行。

如果把同一查询中的 `LEFT JOIN` 改成 `JOIN`，结果变为：

| titre | nb_reservations |
|---|---:|
| Vélo de ville | 2 |
| Tente 2 places | 1 |
| Vélo électrique | 1 |

共 3 行。

注意：电动自行车已经取消的预订也被统计在内。如果只关注有效预订，筛选条件：

```sql
r.statut = 'active'
```

应该放在 **`ON` 条件中**，而不是 `WHERE` 中，否则会使这里的 `LEFT JOIN` 实际上产生 `INNER JOIN` 的效果。

使用 `INNER JOIN` 时，从未被预订过的物品会从结果中消失。这是非常常见的错误，也是 AI 智能体在被要求“列出物品及其预订数量”时经常产生的问题。

### 6.3. 聚合

```sql
SELECT
    u.display_name,
    COUNT(i.id)        AS nb_items,
    AVG(i.tarif_jour)  AS tarif_moyen,
    MAX(i.tarif_jour)  AS tarif_max
FROM users AS u
LEFT JOIN items AS i ON i.owner_id = u.id
GROUP BY u.id, u.display_name
HAVING COUNT(i.id) > 0
ORDER BY nb_items DESC;
```

结果：

| display_name | nb_items | tarif_moyen | tarif_max |
|---|---:|---:|---:|
| Alice | 3 | 6.8333333333333333 | 8.50 |
| Bob | 2 | 8.0000000000000000 | 12.00 |
| Chloé | 1 | 15.0000000000000000 | 15.00 |

共 3 行。

注意三个地方：

- **David 没有出现**：由于使用了 `LEFT JOIN`，分组时实际上存在他的分组，且 `nb_items = 0`；但 `HAVING COUNT(i.id) > 0` 在分组后将其排除了。
- 不可用的物品，也就是 Alice 的电钻，仍被计入，因为没有任何 `WHERE` 条件将其排除。
- 示例中，对 `NUMERIC` 使用 `AVG` 返回了 16 位小数。对于 API，应该在 SQL 端四舍五入，例如 `ROUND(AVG(i.tarif_jour), 2)`，而不是交给前端处理。

两条规则：

- `SELECT` 中没有放进聚合函数的列，通常应写入 `GROUP BY`；
- `WHERE` 在分组**之前**筛选，`HAVING` 在分组**之后**筛选。

## 7. 事务与 ACID

**事务**把多个操作组合成一个不可分割的整体。

```sql
BEGIN;
    INSERT INTO reservations (item_id, borrower_id, date_debut, date_fin)
    VALUES (1, 2, '2026-09-01', '2026-09-05');

    UPDATE items SET disponible = FALSE WHERE id = 1;
COMMIT;
```

如果第二条语句失败，执行 `ROLLBACK` 时，第一条语句的操作也会被撤销。如果没有事务，就可能出现预订记录已经创建，但物品仍被标为可用的情况。

**ACID** 概括了四项保证：

| 属性 | 含义 |
|---|---|
| **A — Atomicity，原子性** | 全部成功，或者全部不执行 |
| **C — Consistency，一致性** | 数据库从一个有效状态转变为另一个有效状态，始终满足约束 |
| **I — Isolation，隔离性** | 控制并发事务之间的相互影响 |
| **D — Durability，持久性** | 已提交的事务即使遇到断电也不会丢失 |

对于项目，尤其要记住：

**任何涉及多张表的业务操作，都应放在同一个事务中。**

例如，创建预订、减少库存、写入历史记录，应该构成一个整体。第 4 讲中，SQLAlchemy 的会话会帮助管理这些操作，但你仍需要理解它在做什么。

隔离性值得进一步说明。两个请求同时预订同一时间段时，可能在任何一方完成写入之前，都检查到“该时间段空闲”。

这就是**竞态条件**，Python 中的 `if` 无法消除它。解决办法应放在数据库层：

- 使用 `UNIQUE` 或 `EXCLUDE` 约束，禁止重复或冲突的数据；
- 或使用显式锁，例如 `SELECT ... FOR UPDATE`。

对于 GearShare，通过约束解决是最简单、最稳健的方式。

## 8. 索引与性能

没有索引时，搜索需要遍历整张表，称为**顺序扫描**，即 *sequential scan*。

对于 100 行数据，这几乎瞬间完成；对于 1000 万行数据，就可能成为严重问题。

### 8.1. 什么是索引？

可以把它理解为技术书籍末尾的索引。

要查找“事务”出现在哪些位置，你不需要重读整本 400 页的书，而是找到索引中对应的词条，再直接翻到第 112 页和第 245 页。

数据库索引的作用与此类似。

具体而言，**索引是独立于表的数据结构**，与表一起保存在磁盘中。对于这里介绍的典型索引，它包含：

- 一列或多列的值，并按顺序组织；
- 指向对应记录在表中物理位置的指针。

PostgreSQL 默认使用 **B-tree，也就是 B 树**：一种平衡树，每个节点覆盖一定的值范围。

假设要在一百万行中找到 `owner_id = 3`，数据库引擎通常只需要沿树向下查找三四步，而不是读取全部一百万行，然后根据指针读取对应记录。

示例中的 `items` 表：

| id | owner_id | titre |
|---|---:|---|
| 1 | 1 | Vélo de ville |
| 2 | 1 | Perceuse |
| 3 | 2 | Tente 2 places |
| 4 | 3 | Vélo électrique |
| 5 | 2 | Vélo enfant |
| 6 | 1 | Ponceuse |

按 `owner_id` 组织的索引可概念性地表示为：

| owner_id | 对应记录 |
|---|---|
| 1 | id 1、id 2、id 6 |
| 2 | id 3、id 5 |
| 3 | id 4 |

由于数据有序，B 树可以加速：

- 等值查询：`WHERE owner_id = 3`；
- 范围查询：`WHERE date_debut BETWEEN '2026-09-01' AND '2026-09-30'`，以及 `<`、`>=` 等；
- 排序：例如 `ORDER BY created_at DESC LIMIT 20`，可以按照已有顺序读取记录。

对于部分文本匹配 `LIKE`，B 树究竟能起到什么作用，你们将在实验中自行测量。

索引的代价：

- **占用空间**：在原文示例中，一张包含 10 万个物品、大小约 7.5 MB 的表，`owner_id` 索引约占 700 KB。
- **写入时需要维护**：每次 `INSERT`、对索引列的 `UPDATE`，以及 `DELETE`，都需要维护索引。
- **是否使用由 PostgreSQL 查询规划器决定**：创建索引不保证它一定被使用。如果查询需要读取表中很大一部分数据，直接扫描整张表可能更便宜。

实际上，你可能已经拥有索引而不自知：PostgreSQL 会为每个 `PRIMARY KEY` 和每个 `UNIQUE` 约束自动建立索引，例如 `items_pkey` 和 `users_email_key`。这也是它快速检查唯一性的方式。

### 8.2. 创建索引

```sql
CREATE INDEX idx_items_owner ON items (owner_id);
CREATE INDEX idx_reservations_item_dates ON reservations (item_id, date_debut);
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

对于前面的表结构，第三个索引是重复的，因为 `email ... UNIQUE` 已经创建了唯一索引。

这里仅用于展示语法，项目中不要重复创建索引。

复合索引 `(item_id, date_debut)` 适用于：

- 仅按 `item_id` 筛选；
- 同时按 `item_id` 和 `date_debut` 筛选。

如果只按 `date_debut` 筛选，它通常作用有限。**列的顺序很重要**，就像通讯录先按姓氏、再按名字排序一样。

**什么时候创建索引：**

- 外键列，如 `owner_id`、`item_id`、`borrower_id`。PostgreSQL **不会**像处理主键那样，自动为外键列创建索引；
- 经常出现在 `WHERE` 中的列；
- 分页列表中用于 `ORDER BY` 的列。

**什么时候不应创建：**

- 表很小时，直接遍历可能更快；
- 列的选择性很低时，例如 90% 的行都为 `TRUE` 的布尔列；
- 不要为了“以防万一”到处建立索引：每个索引都会增加写入成本并消耗空间。

### 8.3. 使用 `EXPLAIN ANALYZE` 测量

通过测量判断，而不是猜测：

```sql
EXPLAIN ANALYZE
SELECT * FROM items WHERE owner_id = 3;
```

`EXPLAIN` 显示查询规划器选择的执行计划；`ANALYZE` 会**实际执行查询**并补充测量结果。

因此要注意：

```sql
EXPLAIN ANALYZE DELETE ...
```

**真的会删除记录。**

下面的示例使用约 10 万行的 `items` 表，记录分属于 1000 个所有者，且 `owner_id` 上**没有索引**：

```text
Seq Scan on items  (cost=0.00..2185.07 rows=99 width=74) (actual time=0.004..3.415 rows=104 loops=1)
  Filter: (owner_id = 3)
  Rows Removed by Filter: 99902
Planning Time: 0.168 ms
Execution Time: 3.446 ms
```

阅读方式：

- `Seq Scan on items`：扫描整张表。
- `cost=0.00..2185.07`：规划器的**估算成本**，使用内部成本单位，主要用于比较不同执行计划。
- 预计 `rows=99`，实际 `actual ... rows=104`：说明统计估算比较准确。
- `Rows Removed by Filter: 99902`：值得关注的信号。PostgreSQL 读取了 100006 行，却只保留 104 行。
- `Execution Time: 3.446 ms`：实际执行耗时。

创建索引：

```sql
CREATE INDEX idx_items_owner ON items (owner_id);
```

同一查询的执行计划变为：

```text
Bitmap Heap Scan on items  (cost=5.06..295.45 rows=99 width=74) (actual time=0.070..0.156 rows=104 loops=1)
  Recheck Cond: (owner_id = 3)
  Heap Blocks: exact=99
  ->  Bitmap Index Scan on idx_items_owner  (cost=0.00..5.04 rows=99 width=0) (actual time=0.058..0.059 rows=104 loops=1)
        Index Cond: (owner_id = 3)
Planning Time: 0.195 ms
Execution Time: 0.340 ms
```

执行计划应**从内向外阅读**，也就是先看缩进最深的执行节点：

1. `Bitmap Index Scan on idx_items_owner`：索引找到 104 条记录的位置。
2. `Bitmap Heap Scan on items`：PostgreSQL 读取表中的这些记录，访问 99 个数据块，即 `Heap Blocks: exact=99`，而不是扫描整张表。

估算成本从 2185 降到 295，执行时间从约 3.4 毫秒降到 0.34 毫秒：**速度提高约 10 倍**。随着表增大，差距还可能扩大。

你会遇到三种扫描方式：

| 节点 | 含义 |
|---|---|
| `Seq Scan` | 读取整张表；对于小表或匹配比例较高的查询，这是正常选择 |
| `Index Scan` | 通过索引逐条找到记录；常见于选择性很高的查询 |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | 先通过索引定位记录，再按数据块读取表；常见于匹配几十或几百行的查询 |

例如，按主键查询通常直接使用 `Index Scan`：

```text
EXPLAIN ANALYZE SELECT * FROM items WHERE id = 4242;

Index Scan using items_pkey on items  (cost=0.29..8.31 rows=1 width=74) (actual time=0.009..0.010 rows=1 loops=1)
  Index Cond: (id = 4242)
Planning Time: 0.203 ms
Execution Time: 0.030 ms
```

对于第 6 节中只有 6 个物品的小数据集，**即使已经创建索引**，你仍可能看到 `Seq Scan`：读取一页表数据，比先访问索引成本更低。

这不是错误，而是查询规划器在正常工作。

实验时请实际操作：创建几千行数据，测量，添加索引，再次测量。数字比口头解释更有说服力。

## 9. 函数、存储过程与触发器

PostgreSQL 不只是保存数据，还能**在数据库端执行代码**。

项目中你们不需要编写很多这类代码，但必须能够阅读。

### 9.1. 函数还是存储过程？

| 比较项 | 函数 `CREATE FUNCTION` | 存储过程 `CREATE PROCEDURE` |
|---|---|---|
| 是否返回值 | 是，可以返回标量、行、表或 `trigger` | 不通过函数返回值方式返回；可使用 `INOUT` 参数 |
| 调用方式 | 在查询中调用：`SELECT ma_fonction(...)` | 使用专门语句：`CALL ma_procedure(...)` |
| 事务 | 在调用方事务中执行 | 在允许的调用环境下，可在内部执行 `COMMIT` / `ROLLBACK` |
| 典型用途 | 计算、触发器 | 批处理、维护 |

使用纯 SQL 编写的简单函数：

```sql
CREATE FUNCTION montant_reservation(p_tarif NUMERIC, p_debut DATE, p_fin DATE)
RETURNS NUMERIC
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT p_tarif * (p_fin - p_debut);
$$;

SELECT montant_reservation(8.50, '2026-09-01', '2026-09-05');  -- 34.00
```

将过去的预订标记为已完成的存储过程：

```sql
CREATE PROCEDURE terminer_reservations_passees()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE reservations
    SET statut = 'terminee'
    WHERE statut = 'active' AND date_fin < CURRENT_DATE;
END;
$$;

CALL terminer_reservations_passees();
```

`$$ ... $$` 用于界定函数或过程主体，避免对其中的单引号逐一转义。

`plpgsql` 是 PostgreSQL 的过程式语言，支持变量、`IF` 和循环等。

### 9.2. 示例：由数据库管理 `created_at` 和 `updated_at`

Web 项目中最常见的需求之一，就是为每条记录添加时间戳。

`DEFAULT now()` 足以提供创建时的默认时间，但存在两个限制：

- 应用程序仍可以主动传入任意 `created_at` 值；
- `DEFAULT` 只在插入时起作用，不会在更新时自动修改 `updated_at`。

因此，可以把这两列交给**触发器函数**管理。PostgreSQL 会在每次 `INSERT` 和 `UPDATE` 之前自动调用它：

```sql
ALTER TABLE items ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now();

CREATE FUNCTION set_timestamps()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        NEW.created_at := now();              -- 插入时：强制设置创建时间
    ELSE
        NEW.created_at := OLD.created_at;     -- 更新时：禁止修改创建时间
    END IF;
    NEW.updated_at := now();
    RETURN NEW;
END;
$$;

CREATE TRIGGER items_set_timestamps
BEFORE INSERT OR UPDATE ON items
FOR EACH ROW
EXECUTE FUNCTION set_timestamps();
```

仔细理解：

- **`NEW`** 表示即将写入的新行，**`OLD`** 表示修改前的旧行，插入时没有旧行。`BEFORE` 触发器可以在真正写入前修改 `NEW`。
- **`TG_OP`** 的值可以是 `'INSERT'`、`'UPDATE'` 或 `'DELETE'`，因此一个函数可以处理这里的插入和更新两种情况。
- **`FOR EACH ROW`** 表示每影响一行，就执行一次函数。
- 该函数具有**通用性**：它没有写死表名。可以分别为 `users`、`items`、`reservations` 创建触发器，复用同一个函数。

验证行为：

```sql
INSERT INTO items (owner_id, titre, tarif_jour, created_at)
VALUES (1, 'Scie sauteuse', 6.00, '1999-01-01')     -- 此值会被触发器忽略
RETURNING created_at, updated_at;

UPDATE items SET tarif_jour = 7.00 WHERE titre = 'Scie sauteuse'
RETURNING created_at, updated_at;                    -- 只有 updated_at 发生变化
```

> 💡 `now()` 返回的是**事务开始时间**，不是当前语句执行时的精确时间。
>
> 因此，同一事务中写入的所有记录会使用相同的时间戳，这通常正是需要的行为。如果需要实际当前时间，应使用 `clock_timestamp()`。

### 9.3. 谨慎使用数据库端代码

触发器对于 Python 代码而言是**不可见的**：阅读服务代码的人，不一定能看出 `updated_at` 会自动改变。

本项目的规则是：

- **可以使用**：简单、通用的技术性规则，例如时间戳和审计；
- **不要使用**：价格计算、预订规则等业务逻辑。这些应放在服务层，以便阅读、通过 pytest 测试，以及在 PR 中审查。

第 4 讲还需要记住：

**Alembic 自动生成迁移时，不会检测函数和触发器。**

必须在迁移中通过 `op.execute(...)` 等方式手动编写，并在 `downgrade()` 中提供对应的 `DROP` 操作。

如果 AI 智能体生成了这类内容，就必须重点审查。

## 10. 在 Docker Compose 中使用 PostgreSQL

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: gearshare
      POSTGRES_PASSWORD: gearshare
      POSTGRES_DB: gearshare
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./sql/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U gearshare -d gearshare"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
```

需要理解三个要点：

1. **命名卷 `pgdata`** 让数据能够在执行 `docker compose down` / `up` 后保留下来。如果没有持久化卷，重新创建容器后数据库会重新变为空。相反，`docker compose down -v` 会删除该卷，相当于“从零开始”按钮。
2. **`/docker-entrypoint-initdb.d`**：这个目录中的 `.sql` 或 `.sh` 文件会自动执行，但**只会在数据目录为空、首次初始化数据库时执行**。如果修改初始化脚本后没有任何变化，原因通常是数据卷已经存在。原文给出的重新初始化方法是执行 `docker compose down -v`，这会删除已有数据。
3. **`healthcheck`** 让其他服务可以等待数据库真正就绪：

```yaml
  api:
    build: ./backend
    depends_on:
      db:
        condition: service_healthy
```

如果没有这个条件，`depends_on` 只会等待容器**启动**，不会等待 PostgreSQL 已经能够接受连接。

于是，你的 API 就可能在启动时因为连接数据库过早而崩溃。这是提交的项目中非常常见的问题。

连接数据库：

```bash
# 从宿主机连接，前提是已经发布端口
psql -h localhost -U gearshare -d gearshare

# 或者直接在容器中连接，无需在宿主机安装 psql
docker compose exec db psql -U gearshare -d gearshare
```

需要了解的一些 `psql` 元命令：

| 命令 | 作用 |
|---|---|
| `\dt` | 列出表 |
| `\d items` | 查看 `items` 表的结构 |
| `\di` | 列出索引 |
| `\x` | 切换为纵向显示，非常实用 |
| `\q` | 退出 |

> 🔒 只有在本地开发时，才可以接受在 `docker-compose.yml` 中明文填写密码。
>
> 项目中，这些配置应该放在**不提交到 Git 的 `.env` 文件**中，同时提交一个 `.env.example`，说明需要哪些环境变量。第 4 讲将正式介绍这一做法。

## 11. 总结

- 关系型数据库提供持久化、**完整性**、并发控制和声明式查询。其中完整性最容易被低估。
- 把必须始终成立的规则放进**数据库结构**：`NOT NULL`、`UNIQUE`、`CHECK`、外键。
- 正确选择类型：金额使用 `NUMERIC`，需要表示时间点的日期时间使用 `TIMESTAMPTZ`。
- 掌握 `JOIN`，知道什么时候需要 `LEFT JOIN`，并掌握 `GROUP BY` / `HAVING` 和 `LIMIT`。
- 一个涉及多张表的业务操作，应当对应一个事务。
- 为外键和常用查询列建立合适的索引，并通过 `EXPLAIN ANALYZE` 测量效果。
- 函数可以返回值，并在查询中调用；存储过程通过 `CALL` 调用。`BEFORE INSERT OR UPDATE` 触发器可以管理 `created_at` / `updated_at`，业务逻辑则保留在应用代码中。
- 在 Compose 中：使用命名卷实现持久化；使用 `healthcheck` 和 `condition: service_healthy` 协调启动顺序；使用 `/docker-entrypoint-initdb.d` 完成初始化。
